Software Processes

Task 1: Introduction

In this workbook, we begin by taking a look at Software Processes - exploring approaches to the systematic engineering of software systems. First take a look at the slides and audio narration linked to above. This provides an illustration of the diverse nature of software systems in order to set the context for our discussion on software development processes. Once you have an understanding of this context, work your way through the remaining tasks in this workbook.

Task 2: Software Processes

Before we begin to tackle some practical activities, it is important to gain an understanding of the nature of Software Processes. View the slides and audio narration linked to above to make sure you have a solid grounding in this area before proceeding.

Task 3: Agile Development

There are many different ways of approaching software development. In this unit, we will be using a form of Agile development. View the slides and audio narration linked above to gain appreciation of the philosophy and principles of Agile methodologies. When you get to the section on “What things do coders like ?” pause for a moment and consider your personal likes and dislikes as a developer.

Task 4: Arrange Meeting with Client

It is important to get the ball rolling as quickly as possible with your project. To this end you should attempt to contact your client contact as quickly as possible to arrange a kick-off meeting.

Agree on a secretary to act as a single point of contact with your client (things will soon get out of hand if everyone is trying to contact the client independently). The secretary should contact the client and arrange an initial kick-off meeting. It is likely that (given the current situation) this meeting will need to be via video conference. Make sure you involve ALL members of the team in the first meeting.

View the slides and audio narration above. The first set of slides outlines 21 Rules of Engagement when communicating with your client and within the team. The other slides provide some useful ideas about what to discuss and the aims and objectives of this first meeting. Be sure to document any important information or decisions that are made when talking to your client.

Hints & Tips:
You may like to create a folder on your repository that contains the minutes to important meetings.

Task 5: Describe Your Project

At some point soon (it may already have happened) you will have a repository for your project. To start with, this repository will look very bare ! In order to make your repository feel a bit more populated, write a short description of your project and save this in the README document. You don’t need to go into a lot of detail - just provide a high-level description of the project as you currently understand it. Be sure however to update this description as the project evolves over time.

The list of stakeholders and user stories that you have identified previously would make ideal additions to the project description. Add these materials to your project description in order to provide more detailed information about the nature and scope of the project.

Task 6: Identify Stakeholders

The first stage towards specifying the requirements for a system is to identify the key stakeholders involved with that system. Using the guidance provided in the slides and audio narration above, identify an initial set of stakeholders for your application. For each stakeholder, record their name and a suitable description of their involvement with the system.

At this stage we don’t expect you to have much detailed knowledge regrading your allocated project. For this reason, you will have to be speculative and take your “best guess” at a list of stakeholders. You can always update this list at a later date - in fact the list of stakeholders will naturally evolve over time on any project (as you gain more knowledge and insight into the application domain).

Task 7: Identify User Stories

Once we have identified a set of stakeholders for a project, we can start to think about what these individuals and organisations might need from a system. Take a look at the slides and audio narration linked above to gain an understanding of the concept of “User Stories”. Once you have some appreciation of these, identify a small set of user stories for your own project. In order to explore the application domain to some extent, you should try to identify a few user stories for each interacting stakeholder (i.e. those stakeholders who directly use the system).

Again, you won’t yet have much detailed knowledge regrading your project, so take a best guess at a set of User Stories. When you meet with your client, you can use this set of candidate stories as the basis for a discussion about the planned system. Again, User Stories can and should evolve over time as you gain more knowledge and insight into your application domain.

Task 8: Create Project Kanban

To help your team manage work (especially now that you are all working remotely) you will need to set up a collaborative ToDo list called a “Kanban Board”. View the slides and audio narrative above for more information about Kanban boards. This year we have chosen to use GitHub to host the Kanban boards (rather than “Jira” as mentioned in the slides), however the basic concepts are the same. To create a Kanban board on GitHub:

  1. Go to the “Projects” tab on your Github repository front page (boards are called “Projects” on GitHub)
  2. Click on the “Projects” dropdown and select “Projects (classic)”
  3. Click on the “New classic project” button
  4. Name the board “Main Kanban” (you must use this name, or we won’t be able to find it !)
  5. Choose the “Basic kanban” template
  6. Click on the “Create project” button

Task 9: Add Some Issues

Each column of the Kanban board contains a set of “issues”. We will be using these issues to represent a wide range of “things to be done” (not just bugs in the code !) Just to get things started, let’s populate your Kanban board with a few initial tasks. Open your Kanban board and add the following “issues” in a suitable position:

  • Write project overview
  • Identify initial Stakeholders
  • Document User Stories
  • Arrange first meeting with client

Make sure that you assign each of these to a member of the team - if it is appropriate, it is possible to assign a particular issue to more than one team member (if it is a group activity). You might have already completed some of these tasks, so feel free to move them to the “Done” column if that is the case.

It is essential that you use the Kanban board to record all of the activities being undertaken on the project. You should also ensure that activities are assigned to particular individuals and that the status of issues are changed when they are in progress and completed. Remember that these issues are a paper trail that provides transparency into the inner workings of the project. If you do work that isn’t covered by an issue on the Kanban board, then that work is invisible and you won’t get any credit for it (when the time comes for marking). For this reason, it is really important to get into the habit of using the board to capture all work activities.

Hints & Tips:
To create a new issue, you first create a “note”, and then convert the note into an issue. This two stage process allows any team member to propose candidate issues, which only become fully-fledged issues when agreed by the team.

Task 10: Gantt chart

A Gantt chart is a really useful tool to visualise how projects work, and should be used in conjunction with the Kanban board. There are lots of different tools available to make Gantt charts, including ones with ways to visualise dependencies within the project (for example, you can’t run tests on the code until some code has been written!).

An example Gantt chart has been provided for you, with the University holidays, Year 2 due dates and assessment periods added, but there may be times you know you won’t be available to work on the project – for example, if you are leaving Bristol for holidays, or around specific religious or cultural festivals. Work out what these are, and mark them out, similar to the way the Assessment Period has been marked, so the Team will know not to assign members tasks at these times.

Start mapping out the processes you’ll need to complete (requirements definition, system & software design, implementation & testing etc) and the tasks you have put on the Kanban board into your Gantt charts, so that you can understand how much time you have for each section. It is important you do this before you meet your client, so you can explain the timeframes of the project to them.

At your client meeting, ask them for any important dates they have between now and May. For example, will they be going on holiday? Do they have times that would be ideal for them to work with you? Do they already know when they can give you data that you might need? After the client meeting, add these to your Gantt chart. The milestones for deploying Minimum Viable Product, Beta Version and Final Release have been added as generic dates, but you may need to being them forward to fit with your clients’ needs.

Make sure that you add your Gantt chart to your Github repository, and that you keep updating it. As with the Kanban boards, if we can’t see the work you have done, it will be invisible and we will be unable to mark it.

Hints & Tips:
You might want to look for a bespoke Gantt chart software and transfer the information into it – but if you do, don’t forget to add it to your Github Repository!

When you’re planning how long things will take, start from the due dates and milestones and work backwards. Always allow for slippage time, and to take into account that you make become sick. So if you know that the client wants the Beta Version released on a certain date, set your own due date for a week earlier, so if things go wrong, you will have some time to fix it.
