## Agile Development

There are many different ways of approaching software development. In this unit, we will be using a form of Agile development.  The slides give a basic introduction to the philosophy and principles of Agile methodologies.

When you get to the section on "What things do coders like ?" pause for a moment and consider your personal likes and dislikes as a developer. 

Agile is a thorough framework with a lot of concepts to get to grips with. Due to time constraints, we are only going to provide an overview of some core principles of Agile to get you started, but if you're interested, look at the original [Agile Manifesto](https://agilemanifesto.org/). In SEP, we would like you to focus on organising your workflow using *Sprints* and *Standups*. At the start of TB2, we will give you an in-depth explanation of more concepts and chance to put them into practice. 

<table><tr><td> <b>Sprints</b> are reoccurring (usually) 2-3 week periods within a longer project which allow a team to organise and think about tasks in smaller time chunks. 
<p></p>
At the beginning of a sprint, the team should have a meeting to discuss all of the work that they believe can be completed within that time period. They should then formalise this task with definable concrete goals which can be evaluated to determine if the task has been completed. </td></tr></table>
<p></p>
<p></p>
<table><tr><td> <b>Standups</b> (A.K.A Daily Standup or Daily SCRUM) are short meetings to keep team members updates on each individual's progress as a sprint progresses. They are named standups as the concept is that everyone should physically standup so that no one gets comfortable enough to allow the meeting to go on for too long - these should only take 15-20 minutes. 
<p></p>
<p></p>During the meeting, each team member will talk about what they have done, what they are *blocked* by and what they are going to do. This format allows everyone to get a quick update on other's progress but also invites team members to help each other with tasks they are blocked by.</p>
<p></p>
<p>To keep this meeting on track, one person should act as the *SCRUM Master* to direct the agenda, make sure everyone is heard and keep the meeting quick. In a full time development team these meetings usually happen daily as the first meeting of the day, however, we understand that this unit is only one of your responsibilities so once or twice per week would be more appropriate.</p>
</td></tr></table>

The stand-ups should be **in addtion to** the regular meetings where you work together as a team.  You should have 1 or 2 a week, and come prepared.  We recommend you rotate the Scrum Master role each time, so everyone in the team gets to experience running the meetings.

### Task 5: Set Up Your Kanban Board and add your first issues

#### Kanban Setup

A Kanban Board is a useful concept taken from the [Kanban method](https://en.wikipedia.org/wiki/Kanban_(development)). It's basically a flexible 'ToDo' list structure, where issues progress through various states (from "ToDo", from "In Progress" to "Done").

It was originally based on post-it notes on a whiteboard, and now there are various digital tools to help you. We are using the GitHub version, called "Projects". 

This is an example of a Kanban board at the end of one of the 2024-5 SEP projects:

![2024-WallProjections Kanban](./02%20Software%20Processes/images/kanban.png)

[Social Housing Tenant Portal](https://github.com/spe-uob/2024-SocialHousingTenantPortal) were the top team of 2025-6 and had an [even better Kanban](https://github.com/orgs/spe-uob/projects/181/views/2), that is so good it doesn't fit nicely into an image! Have a look at how they did it, paying attention to the use of tags and the different columns they had.  You'll see that multiple people can be assigned to the same issue, so you can have some for individuals, teams and sub-sets. 
  
**To create a Kanban board on GitHub:**

1. Go to the "Projects" tab on your Github repository front page (boards are called "Projects" on GitHub)
2. Click on the green dropdown and select 'New Project'.
3. Click on the "New Project" button next to the dropdown arrow.
4. Name the board 'Main Kanban' to make it easier for us to find.
5. Click the green 'create' button in the bottom right.


#### Issues

Each column of the Kanban board contains a set of "issues". We will be using these issues to represent a wide range of "things to be done" (not just bugs in the code!). To create a new issue, you first create a "note", and then convert the note into an issue. This two stage process allows any team member to propose candidate issues, which only become fully-fledged issues when agreed by the team.

Just to get things started, let's populate your Kanban board with a few initial tasks. Open your Kanban board and add the following "issues" in a suitable position.  

- `Write project overview`
- `Identify initial Stakeholders`
- `Document User Stories`
- `Arrange first meeting with client`

Make sure that you assign each of these to a member of the team - if it is appropriate, it is possible to assign a particular issue to more than one team member (if it is a group activity). You might have already completed some of these tasks, so feel free to move them to the "Done" column if that is the case.

**It is essential that you use the Kanban board to record all of the activities being undertaken on the project**. You should also ensure that activities are assigned to particular individuals and that the status of issues are changed when they are in progress and completed. Remember that these issues are a paper trail that provides transparency into the inner workings of the project. 

**If you do work that isn't covered by an issue on the Kanban board, then that work is invisible** and you won't get any credit for it (when the time comes for marking). For this reason, it is really important to get into the habit of using the board to capture all work activities.  

There is more guidance on good issues on the [SEP Knowledge Hub](https://github.com/spe-uob/knowledge-hub/blob/main/Kanban_Guidance.MD) and a [video about how to make your Kanban board](https://uob.sharepoint.com/:v:/r/teams/UnitTeams-COMS20006-2024-25-TB-4-A/Shared%20Documents/General/How%20to%20Git%20videos/5_kanban_board.mp4?csf=1&web=1&e=Oea7iG) and add issues from our former teaching technologist. 

> [!TIP]
> * The Kanban system on Github can be viewed as a board or a table. To change this, click the dropdown arrow next to 'View' in the top left of the screen, under your project name.
> * You might not complete all the tasks in Tuesday's workshop - and that's fine! Add them all to the Kanban so you can keep track of them and tick them off as you complete them.
> * Keep the Kanban board open every time you work on the project, so you can add notes and issues as you go - especially during team meetings and meetings with your mentor - to get into the habit of adding everything to it.
> * **Everyone should always have an issue 'in progress' on the Kanban** - as soon as you move something to 'done', make sure you assign yourself a new task.

### Task 6: Begin writing your README

Your README is the document in the root of your repository which describes what the project is and how to use it. #### Describe Your Project

Right now, your repo looks very bare! In order to make your repository feel a bit more populated, write a short description of your project and save this in the README document. You don't need to go into a lot of detail - just provide a high-level description of the project as you currently understand it. Be sure however to update this description as the project evolves over time.

#### Stakeholders

The first stage towards specifying the requirements for a system is to identify the key **stakeholders** involved with that system. Stakeholders are anyone who might be **impacted** by the system and who might **impact** the system.  They will all have a legitimate vested interest, so we must consider their needs and opinions, even if they don't directly interact with the system.  

Typical stakeholders include:
* End users
* Organisation and system managers
* Organisation and system owners
* General public who are effected by the system - this can be directly (e.g. people who want to use Community Transport) and indirectly (businesses/services people are using the Community Transport to use)
* Legislators (for example, with an interest in GDPR and data privacy)

**Identify an initial set of stakeholders for your application**. Add this to your README and for each stakeholder, record their name and a suitable description of their involvement with the system. You should do this as a whole team, so you all have a shared understanding.  Do NOT use AI tools to help you with this - you need to understand this inside out.  

At this stage we don't expect you to have much detailed knowledge regrading your allocated project. For this reason, you will have to be speculative and take your "best guess" at a list of stakeholders. You can always update this list at a later date - in fact the list of stakeholders will naturally evolve over time on any project (as you gain more knowledge and insight into the application domain). 

> [!TIP]
> * At your client meeting, check if your list is correct - and update the README every time you learn/think about more. 

#### User Stories

Once we have identified a set of stakeholders for a project, we can start to think about what these individuals and organisations might need from a system. We do this through identifying **User Stories**.

A popular way to record user needs is:

> *As a [type of user], I want to [some goal], so that [some reason].*

Or to put it more technically:

> *As a [persona], I want to [action], so that [benefit].*

For example:

> *As a diner, I want to be able to order a meal, so that I can eat it and no longer be hungry.*

> *As a diner, I want to try something new, so I can taste something for the first time and feel happy*.

> *Aa a chef, I want to be able to identify how long it takes to cook meals, so that I have time to cook and deliver and order in a reasonable time*

Once you have identified your user stories, you next identify the **"flow" steps**.  The **"basic flow"** is the normal or typical sequence of steps involved in achieving the goal. 

For example, in a restaurant, when a customer wants a meal, the flow steps as a customer are:

>1. Consider menu
>2. Pick starter
>3. Pick main course
>4. Attract waiter's attention
>5. Place order
>6. Waiter passes order to chef
>7. Chef confirms order with waiter

However, be aware that interaction does not always follow the basic flow:

* **Alternative flow**: another, equally valid, but perhaps less common sequence of steps (sometimes you choose the main course before the starter!)
* **Exceptional flow**: unusual path to cope with strange or undesirable behaviour (you see the price of the food and slip away quietly!)

**Identify a small set of user stories** for your own project, agree them as a team and add them to your README. In order to explore the application domain to some extent, you should try to identify a few user stories for each interacting stakeholder (i.e. those stakeholders who directly use the system).

Again, you won't yet have much detailed knowledge regrading your project, so take a best guess at a set of User Stories. When you meet with your client, you can use this set of candidate stories as the basis for a discussion about the planned system. **User Stories can and should evolve over time** as you gain more knowledge and insight into your application domain.

**DO NOT** use AI tools to help you write User Stories!

### Task 7: Start to Think About Data Protection

If your system (or even you development process) involves the collecting of personally identifiable data, then you will need to adhere to the [UK General Data Protection Regulations (GDPR)](https://ico.org.uk/for-organisations/guide-to-data-protection/guide-to-the-general-data-protection-regulation-gdpr/). The data protection issue that most commonly impacts SEP projects is the collection of cookie data. If you store cookies, you need to embed a cookie consent menu in your web application. There are various libraries that can help you collect your user consent (so you may well not need to build everything from scratch). 

Data protection is an issue that you will need to continuously consider throughout the project to ensure that you have handling user data appropriately and safely. 

**Task**: Start thinking about data protection, and add issues to your Kanban board to make sure you consider it at each stage of your process.  

There are various regulations we all need to consider in any projects we undertake:

**PECR: Privacy & Electronic Communications Regulations**.  This is "Cookie Law" and implements [EU Privacy and Electronic Communications Directive 2002](https://www.legislation.gov.uk/eudr/2002/58/contents)
* Requires websites to get consent from visitors to store or retrieve any information on a computer, smartphone or tablet
* Information should enable users to understand the uses of cookies
* take into account the likely users of the site when explaining
* Information about cookies must be easily accessible after consent
* Information must be given about revoking consent
* Distinguish between first and third party cookies

**GDPR: General Data Protection Regulation**. Governs privacy of all EU Citizens around the world - includes UK through the [Data Protection Act 2018](https://www.gov.uk/data-protection)
* Gives control to individuals over their personal data
* Fines €20 million or 2-4% of the total worldwide annual turnover, whichever is greater.

**What is personal data?**
> * "'[P}ersonal data' means any information relating to an identified or identifiable natural person ('data subject')."
> * "[A]n identifiable natural person is one who can be identified, directly or indirectly, in particular by reference to an identifier such as a name, an identification number, location data, an online identifier or to one or more factors specific to the physical, physiological, genetic, mental, economic, cultural or social identity of that natural person."

**Common categories**
* **Biographical information**: date of birth, National Insurance number, phone number, email address
* **Appearance and behaviour**: eye colour, weight
* **Workplace data and information about education**: salary, tax information, student numbers
* **Private and subjective data**: religion, political opinions and geo-tracking data
* **Health, sickness and genetics**: medical history, genetic data and information about sick leave

**Rules your project MUST follow**
* No personalised data may be processed without unambiguous and individualised consent from the data subject
* The processing of personal data should be limited to what is necessary for the purposes for which they are processed
* Controllers of personal data need appropriate technical and organisational measures (encryption, pseudonymisation or full anonymisation)
* Users always have the right to revoke consent
* You must declare any data collection and purpose for data processing, and state how long data is retained for.

Your client may not know anything about this, but that is not an excuse for poor data practices.  
**If your client asks you to do anything you are uncomfortable with, talk to Sarah about it straight away.**

### Task 9: Gantt chart

![gantt](./02%20Software%20Processes/images/gantt.png)

A key tool of project management is understanding the dependencies between tasks (for example, you can’t run tests on the code until some code has been written!) and what this means for timescales.  It's good practice to start from the deadlines and work backwards, understanding each step you need to take.  In the case of SEP, you know when the deadlines for Minimum Viable Product, Beta Release and Final Release are, so you can work backwards from these.  

A [Gantt chart](https://en.wikipedia.org/wiki/Gantt_chart) is a really useful tool to visualise how projects work, and should be used in conjunction with the Kanban board.  There are lots of different tools available to make Gantt charts, including ones with ways to visualise dependencies within the project.

**Task**: 
* Have a *quick* look for Gantt Chart software and decide what you'll use. You can google for ways to add Gantt Charts to your GitHub Projects, or find common products
* Start mapping out the processes you’ll need to complete the journey to MVP (requirements definition, system & software design, implementation & testing etc).
* Add in the dates you know will impact your project - for example, exam periods, holidays, other coursework deadlines
* Add the tasks from your Kanban board, so you can understand when they need to be done by - for example, if you need to submit your contract by 17 October, what steps need to be taken before then
 
**At your client meeting**, ask them for any important dates they have between now and May.  For example, will they be going on holiday?  Do they have times that would be ideal for them to work with you?  Do they already know when they can give you data that you might need?  After the client meeting, add these to your Gantt chart.  

Make sure that you add your Gantt chart to your Github repository, and that you keep updating it.  As with the Kanban boards, if we can’t see the work you have done, it will be invisible and we will be unable to mark it.  You can see examples of how last year's teams used Gantt Charts from last year:
* [RoboSim](https://github.com/orgs/spe-uob/projects/102/views/3)
* [Breast Cancer Assessment](https://github.com/orgs/spe-uob/projects/110/views/2)


> [!TIP]
> * If you use a Gantt Chart programme, make sure you add it to your README!

### Branch Usage in SEP
The good use of branches are important for organising a project and maintaining a functional version of the product while additional features are being worked on.

Teams must use the **GitFlow** workflow; using the branches *main*, *dev* and feature branches. GitFlow was originally proposed in [this article](https://nvie.com/posts/a-successful-git-branching-model/). Although we are asking you to use GitFlow for this project, it is worth noting that some software development teams use an alternative method called [Trunk-Based development](https://www.atlassian.com/continuous-delivery/continuous-integration/trunk-based-development) which you may come across in the future.

**Feature branches** should be made when adding a new feature to the project. Once a feature is fully implemented the branch should be merged into *dev* via a pull request and then deleted. This prevents your remote repository being filled with "stale" branches.

The *main* branch should have a functioning version of the project on it at all times. When you are ready for a release (i.e. MVP, Beta, Final), *dev* should be merged into *main* so it's up to date with the functioning last version.

**DO NOT MERGE FEATURES DIRECTLY INTO MAIN**
