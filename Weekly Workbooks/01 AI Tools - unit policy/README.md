## 'AI' Tools
You **are** allowed to use 'AI' tools like ChatCPT, Co-Pilot, MidJourney etc in your project but there are some important caveats.  

You wouldn't be marked down for using AI tools, as long as you are also writing your own code as well - but **you would be marked down** if you use AI tools without thought behind why, what value they add and what the risks are, or if we find out you've been using them without telling us. Using, for example, ChatGPT to write your README because it's faster and it is likely to be grammatically correct would not be a good reason - but using an AI tool to help bug-catch, **as part of a suite** of other bug-catching methods, including things written by each team member, which you explain in a sentence in your repo, would. 

**If you want to use AI tools to save you time**, make sure you're factoring in the additional overheads, some of which are below - you might find that it actually takes longer to understand, test and bug-fix generated code than it would be to write code yourself. 



# 
### What do we mean by 'AI' tools?
Anything that uses Large Language Models (LLMs for example ChatGPT, Claude, CoPilot etc) or Generative AI (for example to create pictures, eg Midjourney, Dall-E etc). Given how fast the sector is moving, there are bound to be new examples popping up all year, so if you're uncertain if something counts, please [ask](https://teams.microsoft.com/l/channel/19%3A234d66b3097d4baeaf04abfdef596bc2%40thread.tacv2/Questions%20and%20Answers?groupId=843eb232-1d99-4994-9266-7ee9638bb6d7&tenantId=b2e47f30-cd7d-4a4e-a5da-b18cf1a4151b).  When we say 'AI' tools, we also mean using [vibe coding](https://en.wikipedia.org/wiki/Vibe_coding) and any other concepts that appear over the year.

#
### Do NOT use 'AI' tools for writing your README!
It's really important that everyone in the team knows, understands and owns everything that is written in the README, and this can't happen if something else has written it for you. In particular:

* **User Stories** should be driving your project, and are where you demonstrate you really understand your clients' needs.  There is NO good usecase for outsourcing these!

* **Project Description** can't be written by anyone/thing else if you really know your project - if you don't, you will not get good marks.

* **AI tools [hallucinate](https://en.wikipedia.org/wiki/Hallucination_(artificial_intelligence))** a **lot** more than you might think, and you definitely can't trust them for your user or developer instructions.

If you're feeling insecure about your writing and think that the tools will help you, you are looking for help in the wrong places - instead, ask your team-mates to proof-read your work. This is standard in employment, and helps ensure everyone knows everything in your README inside-out. It will also help you understand if you're making errors and how to fix them. 

**If you are worried about the quality of your written English**, the University has lots of [Study Skills support](https://www.bristol.ac.uk/students/your-studies/study-support/study-skills/) including [drop ins](https://alt.content.bris.ac.uk/bbcswebdav/courses/Study_Skills/whats-on/index.html?source_domain=www.ole.bris.ac.uk#/id/632acb7dfb7af103d447e4c6) and [bookable tutorial](https://alt.content.bris.ac.uk/bbcswebdav/courses/Study_Skills/whats-on/index.html?source_domain=www.ole.bris.ac.uk#/id/5f044158cf57ca06c433abe4) with Study Skills tutors, as well as [workshops](https://www.bristol.ac.uk/students/your-studies/study-support/study-skills/workshops/) and [written resources](https://www.bristol.ac.uk/students/your-studies/study-support/study-skills/). Getting support will help you much more in the long run than relying on tools that may not be accurate.

We'd like to know what you're using, and how, for a number of reasons apart from it being Faculty policy: 

* It's good practice to list and cite your tools and how you're using them - you need to get used to doing this for your final Individual Projects

* We are interested! You're probably finding new tools and new ways to use them as they're emerging, and it's exciting times for Computer Science. 

* Sharing what you're finding is useful for other students - whether it's other students looking at your repo, or us being able to recommend tools to future years

* We want to know what is your work and what is done by tools.   

#
### If you use AI-generated code, you will still need to understand exactly what it's doing
You will have to be able to answer detailed, technical questions about your code from your team-mates, clients and in the vivas. This could include exactly what a section of the code does, or why the code is structured in a certain way, and you should definitely be asked by team-mates during code reviews and dealing with merge conflicts.  

#
### If you are using AI-generated code, your team-mates will have to do code reviews on it
This means you cannot just drop a large piece of generated code into a PR and expect your team-mates to work it out - if this happens, your team-mates are allowed to ignore it and not review it until you have broken it down into smaller, manageable PRs, clearly labelled, commented, in sensible-sized chunks that are clearly defined features.  It is **your** responsibility to make sure team-mates can work with it, not theirs!

Large code dumps are ignored in the marking anyway, as these are usually libraries, code from elsewhere and if they *are* students' own work, it's bad practice.


#
### NEVER input any proprietary code/business information into LLMs
Remember **everything** you enter into AI tools is instantly visible to and usable by the service provider, and is instantly out of your control.

If your project includes any proprietary code or code from a client, or information about how they work as a business, you **cannot** input this into LLMs, as anything you input **will** be used to train models and used in other ways. 



#
### Write extra tests for any AI-generated code
As we will talk about in Week 4, we want you to use **Test-Driven Development** where you write tests for your code before you write the code, that can then be part of your Continuous Integration processes. 

If you are using AI-generated code, you will need to make sure you've got tests in place for it.

#
### You are *always* expected to write your own tests! 
Knowing how to write your own code tests is very important, and every student is expected to write your own tests from scratch. If you decide to also include some AI-generated tests, make sure you tell us in the `AI Tools` file in your `docs` folder and what percentage of tests were AI-generated and written by the team.

#
### If AI-generated code goes wrong, YOU are responsible!
Bear in mind that if something goes wrong with code written by LLMs, you will be seen as **MORE** responsible than if you wrote the code yourself, because you have made the active decision to outsource the coding and take the associated risks. 

Especially if you are developing something that will use your client's data, interact with their systems etc, you will need to have tested generated code even more rigorously than your own, because hallucinations are still very common. 

#
### If you use AI Tools, you will still have to do enough work to pass the unit
You are expected to spend ~6.5 hours/week on SEP and to create a Minimum Viable Product with stretch goals. If you use AI tools to reduce time taken on tasks, you will still need to spend the total time elsewhere.  

For example, there are tools that can convert Figma outputs into React JS.  If you use these to save time, you will need to think about what other features you can make, so you are doing enough work to pass. Remember, SEP is assessed on how you work in a team environment and that you are using mature and repeatable software development processes, so if you find a shortcut in one area, you will be expected to push yourself in others. 


#
### What if you think a team-mate is using AI tools/vibe coding and not declaring it?
 - **If it's a large code dump they expect you to review** first ask them if they wrote it themselves, and second, say you cannot review it until it is broken down into smaller PRs around individual features.  If it's not clearly commented or would take too much time to work it out, reject it and explain why.  If they complain, direct them here!

- **Ask them!** This shouldn't be a shameful or scary thing to ask - if they say yes, remind them to add the info about it to the AI folder in the README.  If they say no, but you have concerns, come and talk to Sarah - Teams is easiest, or in the drop-ins.
