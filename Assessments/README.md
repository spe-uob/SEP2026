# How is the unit assessed?

Assessment for the Software Engineering Project is based on a range of different metrics.  Remember, unlike other units, you are measured on the **process** rather than on the outputs, and because each project is unique, this will look different for every project - although we use the [University's standardised Year 2 marking scheme](https://bristol.ac.uk/media-library/sites/academic-quality/documents/taught-code/annexes/university-marking-criteria-level5.pdf) to help us decide the marks.

Students receive **individualised marks**, based on your performance, so it is possible that within the team, there make be students who receive a high First Class mark (over 70), students who fail (under 40) and students in between.  Students who don't engage in the project can and will fail, and have to attend the bootcamp in the summer reassessment period, which includes an intensive week-long team project.

The metrics we use to mark the project include:

**Team project presentation and demo (viva)** 
This takes place in the summer exam period (4-22 May 2026).   
There will be opportunities to practice and get feedback on your team's performance in formative (unmarked) vivas in Weeks 10 and 19.  The formative vivas will take place in groups, where you can watch and give peer feedback to other teams, using the same marking criteria that will be used in the final viva. The final summative (marked) vivas will only be given to the markers.  

The viva gives us the team mark, which is then individualised using a combination of:

**Github metrics**
Each student's contribution to the codebase, number of meaningful commits, pull requests, code reviews and kanban board tasks completed. 

Please note:  we discount both very small commits and very large commits (for example, changing a font colour, or dropping in tutorial/library code). 

**Peer feedback** 
You will give private feedback on each team-mate's performance at the end of the project.  This will be feedback on contribution to the code base, contribition to the project management and contribution to the overall project develioment

**Mentor reports**
Your Teaching Assistant mentors will be giving feedback on the Team and individual performance throughout the year, and at the end of the project.  This will include examples of good practice and problems the team has overcome. 

> [!NOTE]
> The GitHub metrics, peer feedback and mentor reports are taken together, to triangulate the student's performance - so someone who, for example, has fewer GitHub metrics than team-mates, but has contributed more to the project design and management, will not be penalised.

# How to release to the client

You are expected to release code to the client **at least 3 times over the life of the project**.  This is usually:
* Minimum Viable Product (MVP) - no later than 20 November 2025 (Week 9)
* Beta Release - no later than 19 February 2026 (Week 17)
* Final Release - no later than 30 April 2026 (Week 24)

Please note:  you can release earlier! If your project is moving at a different rate, don't feel you have to wait until the deadline.  **Discuss the dates with your client well in advance** and get meetings booked in early, so you're not delayed by clients' busy-ness. 

In Software Development terms, the **Final Release** is when the code is released to the live environment so users can use it.  A **Beta Release** is a pre-release that in business is when a relatively large group of users can try it out, before it's finalised, to help find bugs etc.  A Beta Releae can be 'closed', so only specific users can use it (as in SEP) or 'open', where anyone can use it, understanding it my be buggy/not be the finished product.  

For our releases, there are a number of steps to undertake:

## 1. Push the code to Main
You will continue developing on the dev branch.

## 2. Share the product with the client
This will look very different depending on your client's wants/needs, how technically adpet they are etc. This could be:
* A meeting online or in person to walk them through the system so far (set this up in advance!)
* Forking your repo so they can try it out (only for technically adept clients - make sure you have good user instructions in the README!)
* Sending your client videos of how it works/screenshots etc

## 3. Ask the client for feedback!
If you are not releasing in a meeting, you should have a meeting set up or another way to get feedback from them (arrange this in advance!)

## 4. Complete the release checklist and upload it to Blackboard
* Download the [Release checklist](https://github.com/spe-uob/SEP2024/blob/main/Assessments/Release%20checklist.md) and complete it. We don't expect you to have completed every box at MVP stage - add any issues you've faced or delays into the notes section
* Save the checklist as a PDF
* One member of each team uploads the PDF to the unit Blackboard under Assessment, Submission & Feedback

> [!NOTE]
> Some of you may be sharing your project much more frequently - just pick the date of the release as the one nearest to the deadline to be the nominal MVP/Beta/Final
