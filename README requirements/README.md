# What to include in your README

In week 2, we introduced the purpose of the [README](https://github.com/spe-uob/SEP2025/tree/main/Weekly%20Workbooks/02%20Software%20Processes#task-6-begin-writing-your-readme) and asked you to write a project description, identify stakeholders and create user stories. Now that your project is off the ground we'd like to lay out the full requirements of the README.


> [!IMPORTANT]
> You should **NOT** use AI tools to help you write these!  As we told you in Week 2 and in the [Unit Policy on AI](https://github.com/spe-uob/SEP2025/tree/main/Weekly%20Workbooks/01%20AI%20Tools%20-%20unit%20policy#ai-tools---unit-policy), the README is what defines your project, and if someone/something else has written it for you, you can’t own it in the same way. 
>  
> If you are worried about your writing, ask your team mates to proof read for you - this will help them understand too.  We would see badly-written English than the mid English produced by an LLM that doesn’t mean anything as it’s not connected to your project.

## README requirements:

- **Project Description:** A good description of the project should provide anyone who has not previously interacted with the project a quick overview of what you are trying to achieve. It is best to avoid technical detail here and keep the description at a high level.

- **[Stakeholders](https://github.com/spe-uob/SEP2025/tree/main/Weekly%20Workbooks/02%20Software%20Processes#stakeholders):** The list of stakeholders should introduce everyone who takes an interest in the end product and give a brief description of how and why they will use the system. Where appropriate, try and group users into major categories. For example, if you are creating an app for SCUBA diving training, you might want to identify *users* as either 'Diving Instructors' or 'Trainees'.

- **[User Stories](https://github.com/spe-uob/SEP2025/tree/main/Weekly%20Workbooks/02%20Software%20Processes#user-stories):** allow software engineering teams to stay grounded in *why* the system will drive benefit to users instead of tunnel-visioning on the technical details. You should include at least 3 user stories in your README. Look at the [https://github.com/spe-uob/SEP2025/tree/main/Weekly%20Workbooks/02%20Software%20Processes#user-stories) or [this article](https://www.atlassian.com/agile/project-management/user-stories) for more guidance.

- **Project Structure:** from a development perspective, getting to grips with a new software repository can be a challenge to begin with. Including an overview of where the major components of the system is really useful to others who might pick up the project in the future. You don't need to describe every file but signposting important files or directories should be the goal. e.g. where are the database config files, where are the tests, etc.

- **Architecture Diagram:** this should be a high level diagram that makes it easy for a *new developer* on the project to understand how the system works.  You can find information about the different kinds of diagrams in the [slides in the Week 3 workbook](https://github.com/spe-uob/SEP2025/tree/main/Weekly%20Workbooks/03%20Architecture%20-%20Technology%20Stacks#architecture---technology-stacks) - put any other diagrams you make in a subfolder of your repository `docs` folder.  Tools you might want to use are [draw.io](https://app.diagrams.net/), [LucidChart](https://www.lucidchart.com/pages/) or [Miro](https://miro.com/diagramming/what-is-software-architecture-diagramming/).


- **User Instructions:** should give detailed instructions for how the *end user* accesses the app. These could be as simple as pointing them to a website URL or downloading and running an executable. If they need to install anything on their own systems, include instructions. Remember to write these in sufficient details that someone with limited technical knowledge can follow them.

- **Developer Instructions:** should give details instructions for how a *new developer* on the project would go about picking up where you left of and continuing the development. This could be something like cloning the repo and opening to code base within an appropriate IDE or how to request access for the cloud resources. If you have used APIs in the project, include the keys in here.  This will be the basis for your handover document at the end of the project. 

Begin by writing as many of these sections as possible.  It might not be possible to write them all yet, i.e. user instructions, but put the headings in place to show where the information will go.  You should then continue to update the readme as the project progresses so that it is always up to date and accurate - you might want to add this as a weekly task in your team meetings.

> [!TIP]
> The sections above are required but you can add more sections if you think they're appropriate.
> Have a look at the [strong projects from last year](https://github.com/spe-uob/SEP2025/tree/main/Weekly%20Workbooks/02%20Software%20Processes#task-10-look-at-previous-repos) for examples of things you could add.

## Important documents to have in the README

You also need to have a number of documents at the top level of your repo. We've talked about these in the lectures, and the hyperlinks take you to the workbook links:

- **`AI document`**: Every time you use an AI tool, add it to your AI document, telling us what you used, why and how.  Please make sure all your team has read and understand the [Unit AI Policy](https://github.com/spe-uob/SEP2025/tree/main/Weekly%20Workbooks/01%20AI%20Tools%20-%20unit%20policy).

- **Folder for other diagrams**: Make it easy for us to find all the lower level diagrams explaining your Architecture

- **`LICENSE` document**: Push the [Software Licence](https://github.com/spe-uob/SEP2025/tree/main/Weekly%20Workbooks/03%20Architecture%20-%20Technology%20Stacks#software-licences) you have chosen at the top level.

- **`ETHICS.md`**:  Push a document explaining which [ethics category](https://github.com/spe-uob/SEP2025/tree/main/Weekly%20Workbooks/02%20Software%20Processes#task-8-ethical-issues) your project falls under.  Most will be under the Blanket Ethics Agreement.
